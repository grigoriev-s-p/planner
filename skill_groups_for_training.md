# Группы навыков для рекомендаций по дообучению

## Основание

Источник: `data/raw/dataset.xlsx`. Для анализа использована нормализованная таблица `data/processed/engineer_skills.csv`, связанная с исходным файлом через `data/processed/_dataset_manifest.json`.

В датасете:

- 30 инженеров с указанными навыками;
- 182 связи «инженер — навык»;
- 116 уникальных названий навыков;
- медиана — 6 навыков на инженера, 75-й перцентиль — 7;
- 86 из 116 навыков встречаются только у одного инженера.

Из-за большого количества единичных навыков группировка только по совместной встречаемости была бы нестабильной. Ниже объединены два сигнала: фактические сочетания навыков в датасете и технологическая близость, то есть общая платформа, язык, инструментарий и тип решаемых задач.

Самые заметные сочетания в данных:

- Java + PostgreSQL — у 5 инженеров;
- REST API + SQL — у 5;
- REST API + Usability — у 5;
- Postman + SQL — у 4;
- Java + Spring Boot — у 3;
- Docker + Kubernetes — у 2;
- JavaScript + GraphQL — у 2;
- Python + Hadoop — у 2;
- BPMN + UML — у 2.

## Рекомендуемый размер группы

Оптимальный размер основной группы — **6–10 канонических навыков**, целевой ориентир — **8**.

Почему:

- группа такого размера сопоставима с реальным портфелем одного специалиста в датасете: обычно 6–7 навыков;
- внутри группы остаётся достаточно кандидатов для рекомендации после исключения уже известных навыков;
- группа ещё не становится слишком широкой: Java и React не попадают в один набор только потому, что оба относятся к разработке;
- 116 исходных навыков раскладываются примерно на 15–18 предметных групп без искусственного объединения несвязанных стеков.

Допустимые исключения:

- 4–5 навыков для самостоятельных стеков, например .NET или автоматизация тестирования;
- до 12 навыков для инструментального контура, например DevOps или ручное и API-тестирование;
- при росте группы свыше 12 её стоит делить на подгруппы.

Количество навыков не должно быть жёстким правилом. Лучше оставить небольшую связную группу, чем добавить нерелевантные технологии ради размера.

## Нормализация названий

Перед расчётом рекомендаций стоит привести дублирующиеся и близкие названия к каноническим навыкам. Исходные названия при этом можно сохранить для отображения.

| Канонический навык | Исходные варианты |
| --- | --- |
| Spring Core | Core; Core Spring; Spring Core; Spring Framework |
| Kafka | Kafka; Apache Kafka |
| Микросервисы | Microservices; Микросервисы; Microservices Архитектура |
| CI/CD | CI/CD; GitLab CI; CI/CD (GitLab, Jenkins) |
| Функциональное тестирование | Функциональное тестирование; Regression/Smoke/Functional testing |
| Регрессионное тестирование | Регресс; Regression/Smoke/Functional testing |
| REST-интеграции | REST API; REST/SOAP интеграции; REST/gRPC |

Не все строки в этой таблице являются полными синонимами. Например, `Microservices Архитектура` содержит архитектурный акцент, а `REST/gRPC` объединяет два протокола. Для поиска близости их можно связать с каноническим понятием, но в профиле инженера лучше сохранять исходную детализацию.

## Как строить рекомендации

Рекомендуемый порядок сигналов:

1. Исключить навыки, которые уже есть у инженера после нормализации алиасов.
2. Найти кандидатов из тех же основных групп, что и известные навыки.
3. Повысить кандидатов, которые фактически встречались вместе с известными навыками у других инженеров.
4. Учесть роль инженера и технологическую последовательность: язык → основной фреймворк → данные и интеграции → эксплуатация.
5. Добавлять навыки соседних групп только при наличии мостового навыка или явной рабочей потребности.
6. Показывать не более 3 основных рекомендаций одновременно и указывать, какой известный навык послужил основанием.

Пример весов для ранжирования:

- 40% — близость в основной группе;
- 30% — совместная встречаемость в исходном датасете;
- 20% — соответствие роли;
- 10% — связь с соседней группой или технологической последовательностью.

Для навыка, который встречается в датасете один раз, совместная встречаемость не должна быть решающим фактором. Рекомендация должна подтверждаться группой и ролью.

## Примеры корректных траекторий

- Java → Spring Core / Spring Boot → Hibernate → PostgreSQL → Kafka или Docker.
- JavaScript → TypeScript → React, Vue.js или Angular → GraphQL / REST API.
- SQL → Pandas / Power BI / Tableau для аналитика либо Python → Hadoop / Spark для Data-направления.
- Docker → Kubernetes → CI/CD → Terraform / Prometheus.
- Ручное тестирование → Postman / DevTools → Playwright или Selenium WebDriver → CI/CD.
- Swift → UIKit или SwiftUI → CoreLocation / ARKit.
- Kotlin или Java → Android SDK → Jetpack Compose → Room / Dependency Injection.
- C# → .NET Core → ASP.NET → Entity Framework / LINQ.
- BPMN / UML → Системный анализ → REST API → Проектирование интеграций.

## Ограничения

- Датасет небольшой: 30 инженеров недостаточно для устойчивого машинного обучения эмбеддингов или автоматического community detection без внешних знаний.
- Наличие навыка не содержит уровня владения, длительности опыта и даты последнего применения.
- Редкие навыки могут быть важными, хотя статистически почти не влияют на совместную встречаемость.
- Группа определяет близость, но не заменяет проверку prerequisites. Например, React логично рекомендовать после JavaScript, а Kubernetes — после базового опыта с контейнерами и Linux.
- Для production-рекомендаций следует дополнительно учитывать спрос задач, дефицит компетенции, Bus Factor и свободную ёмкость инженера.

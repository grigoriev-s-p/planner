# Planning core

Модуль содержит reusable feasibility checker и детерминированный planner на
шесть спринтов. Первичная цель — закрыть максимум полных инициатив; scoring v1
упорядочивает задачи внутри initiative-aware выбора.

## Правила planner v1

- **Eligibility по ролям.** До scoring модуль `eligibility.py` проверяет, что
  для каждой роли с положительными `required_hours` существует хотя бы один
  инженер с тем же нормализованным `role` среди всех команд. Если роли нет, задача получает
  `INELIGIBLE_DATA_CONSTRAINT` и причину `NO_AVAILABLE_ROLE_SPECIALIST`,
  сохраняется в отчёте и не передаётся в planner. Количество доступных часов на
  этом шаге не проверяется.
- **Cross-team (подтверждено организаторами).** Инженер может помогать другой
  команде при наличии свободных личных часов. Для каждой роли сначала используются
  инженеры команды задачи, затем — остальных команд; внутри группы порядок:
  больше оставшихся часов, затем `engineer_id`. Роль сравнивается точно по
  каноническому `role`; переданные требования к skills также обязательны.
  Каждая уникальная пара `(engineer_id, team_id)` имеет отдельный bucket
  `80 * capacity_rate`; одинаковые дубли строк не создают новый ресурс. Общий
  лимит инженера равен сумме его team-specific buckets.
  SP списываются только с `task.team_id`; SP команды привлечённого инженера не тратятся.
  Назначение хранит `engineer_id`, `source_team_id`, `teams`, `task_team`,
  `assigned_task_team_id`, `role`, `allocated_hours`, размер исходного bucket,
  использованную долю `capacity_share` и `cross_team`. Для совместимости
  сохраняется поле `hours`.
  `cross_team = true`, если `source_team_id` отличается от команды задачи.
- **Atomic allocation.** Для каждой `ToDo` и `InProgress` задачи создаётся копия
  всех SprintState. Часы и SP коммитятся только после полного размещения задачи
  не позже Sprint 6. Неуспешная симуляция получает `MOVED` с конкретными
  ресурсными причинами, а пробные allocations помечаются `ROLLED_BACK` и не
  занимают ресурс. `OUTSIDE_QUARTER` используется только когда подтверждённый
  самый ранний спринт старта или завершения находится после Sprint 6.
- **Scoring.** Среди готовых по зависимостям задач planner выбирает максимальный
  `TaskScore` из отдельного `scoring.py`. Базовая часть учитывает `rung`, статус
  и мягкую срочность `planned_end`; динамическая — завершение инициативы и
  разблокировку downstream задач. После commit динамическая часть
  пересчитывается. При равенстве используются `InProgress`, более ранний
  `planned_end` и `task_id`. Организаторы подтвердили: выше `rung` — выше приоритет;
  default configuration использует `higher_is_better`, вес 40 больше каждого
  другого отдельного веса. Формула и остальные проектные допущения описаны в
  [SCORING.md](SCORING.md).
- **Initiative objective.** Перед выбором задачи planner без коммита проверяет,
  можно ли завершить все оставшиеся задачи инициативы. Для пяти или меньшего
  числа надёжных инициатив он перебирает порядок их полного выполнения и
  выбирает вариант с максимумом завершённых инициатив. При равном количестве
  применяются больший `rung` и детерминированные tie-breakers. При большем
  количестве сохраняется initiative-aware эвристика; частичные задачи
  рассматриваются только после отсутствия полностью выполнимой инициативы.
- **Team reassignment.** Для задачи проверяются только команды, уже присутствующие
  в team history или профилях инженеров. Исходная команда сохраняется как
  `original_team_id`, выбранная — как `assigned_team_id`. При одинаковом сроке
  остаётся исходная команда; перенос выполняется, если она невыполнима или другая
  команда завершает задачу раньше. SP списываются с `assigned_team_id`.
- **Scoring и feasibility.** Свободные SP, часы, роли и инженеры не входят в
  business score. Высокий score не обходит ресурсные и dependency constraints.
- **Dependencies.** Временное направление:
  `blocking_task_id -> blocked_task_id`. После завершения blocker в Sprint N
  зависимая задача может начаться с Sprint N+1.
- **Multi-sprint SP.** Полный `task_story_points` остаётся атрибутом задачи.
  Дробный `capacity_sp_load` каждого активного спринта равен
  `task_story_points * allocated_hours / total_required_hours`. Поэтому SP-load
  отражает ту же долю работы, что и часы, а свободная SP capacity одновременно
  ограничивает максимальное число выделяемых часов. Сумма load равна task SP с
  допустимой погрешностью floating point. `planned_completion_sp` равен полному
  SP только в прогнозном спринте завершения, а `completed_sp` у прогноза остаётся
  нулём. При неуспехе атомарная симуляция откатывает оба ресурса. Внешние
  инженеры не изменяют SP capacity и не переносят нагрузку на свои команды.
- **SP без часов.** Если SP есть, а положительной оценки часов нет, planner
  возвращает `STORY_POINTS_WITHOUT_HOURS` и распределяет SP-load
  по доступной capacity без выдумывания часов.
- **Recommendations.** Успешное переназначение сохраняется как доступная
  `REASSIGN_TO_EXISTING_TEAM`. Для задачи, которую не может завершить ни одна
  существующая команда, переназначение помечается недоступным, а
  `MOVE_TO_NEXT_QUARTER` — доступным. Planner сохраняет объяснение и не создаёт
  новые команды.
- **Baseline dates.** `planned_start` и `planned_end` сохраняются как baseline и
  не являются hard constraints. Forecast хранится отдельно. Если вызывающий код
  передал `quarter_start_date`, Sprint N отображается диапазоном в 14 дней;
  forecast start равен началу первого спринта задачи, forecast end — последнему
  дню спринта завершения. Без даты начала квартала календарные forecast и shifts
  остаются пустыми.
- **Reasons.** `final_reasons` объясняет итоговый статус. `placement_attempts`
  отдельно хранит отклонённые, подтверждённые и rollback-попытки со спринтом и
  reason codes. Совместимое свойство `reasons` возвращает только final decision.

Ресурс команды рассчитывается через capacity layer как
`mean(team_history.velocity_achieved) * 0.8`. Ресурс инженера для каждой команды —
`80 * capacity_rate` часов на спринт. Суммарный ресурс инженера равен сумме его
отдельных командных buckets.

## Ограничения данных

В датасете нет явной даты начала квартала, отдельного hard deadline и связи
задачи с требуемыми технологиями. `spent_time` не распределён по ролям, поэтому
planner не вычитает выдуманный прогресс из `InProgress`. Skill constraints
применяются только при передаче отдельного справочника
`task_id / role / technology`.
